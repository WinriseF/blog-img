Why Faster AI Coding Does Not Always Mean Faster Developers

A strange change is taking place in software development. Artificial intelligence can now write functions, repair bugs, run tests, edit several files, and even work on a task in the background while a developer does something else. Yet a simple question remains surprisingly difficult to answer: does all of this actually make programmers faster?

The obvious answer seems to be yes. Modern coding agents can perform work that once required many small manual steps. GitHub describes its Copilot coding agent as an autonomous system that can take a task, work in its own development environment, and return with a pull request for a human to review. Its command-line version can plan tasks, edit files, run tests, and continue working through several steps. Similar agent-based tools have appeared across the software industry.

This is different from the first generation of AI coding assistants. Earlier tools mainly predicted the next line or suggested a short block of code. The developer remained in control of almost every action. An agent can operate at a higher level. A programmer might ask it to add a feature, investigate a failing test, or update documentation. The agent then decides which files to inspect, what changes to make, and which commands to run.

That shift matters because typing code is only one part of programming. Developers spend large amounts of time reading unfamiliar code, understanding requirements, searching documentation, running tests, reviewing changes, and discovering why an apparently simple fix breaks something elsewhere. An agent that handles several of these steps could remove much more work than an autocomplete system that merely helps people type faster.

But measuring the benefit is harder than watching an impressive demonstration. In 2025, the research organization METR ran a randomized controlled trial with 16 experienced developers who worked on large open-source projects they knew well. The researchers collected 246 real tasks, including bug fixes, new features, and refactoring work. For some tasks, developers could use artificial intelligence tools. For others, they could not.

The result surprised both the developers and the researchers. When AI tools were allowed, the developers took about 19 percent longer to finish their tasks. Before the experiment, they had expected AI to make them roughly 24 percent faster. Even after completing the study, they still believed that AI had saved them time.

This finding does not mean that AI coding tools are generally useless. METR was careful to say that its experiment covered a particular situation: experienced developers working in mature repositories that they already understood deeply. The study also used early-2025 tools, while coding models have continued to improve. Still, the result reveals something important about productivity. A tool can feel fast without making the entire job faster.

One reason is verification. An AI system can produce hundreds of lines of code in seconds, but a human still needs to decide whether those lines are correct. Reading generated code can be slower than writing a familiar solution directly, especially when the output contains subtle mistakes. A developer may also spend time explaining the task, waiting for the model, correcting its approach, and checking changes that would never have been necessary without AI.

Experienced developers face another problem: they possess knowledge that is difficult to put into a prompt. A person who has worked on the same project for years may know that a certain design looks attractive but caused trouble before, or that a small function depends on an undocumented assumption elsewhere in the system. The code itself does not always contain this history. An AI agent may therefore produce a reasonable solution that does not fit the project's hidden rules.

This helps explain why benchmarks and real work can tell different stories. Coding benchmarks usually provide clearly defined problems with tests that determine whether a solution succeeds. Real software projects contain incomplete requirements, style expectations, historical decisions, security concerns, and trade-offs that cannot always be reduced to a test result. METR noted that benchmarks are useful, but they may not directly measure the effect of AI on everyday development.

At the same time, coding agents are becoming more capable of handling the surrounding workflow. GitHub's tools, for example, can now work from issues, create draft pull requests, perform self-review, and operate in environments where tests and security checks are available. GitHub has also integrated multiple coding agents into the same repository workflow, giving them access to code history, issues, pull requests, and repository instructions. The goal is no longer simply to generate better code. It is to give the agent enough context to behave more like a useful member of a software team.

This suggests that the largest productivity gains may come from changing how work is divided rather than making a programmer type faster. A developer can delegate a well-defined background task, continue working on another problem, and later review the result. Repetitive jobs such as adding tests, updating documentation, investigating simple bugs, or making routine changes across many files may be especially suitable. In these cases, even an imperfect agent can be valuable if checking its work takes much less time than doing the whole task manually.

The opposite is true when a problem depends heavily on judgment. If requirements are unclear, architecture is changing, or errors are expensive, continuous supervision can remove much of the advantage of automation. The human may become a manager of machine-generated work, spending less time producing code but more time reviewing decisions. Productivity then depends on whether this new form of supervision is cheaper than the work it replaces.

There is also a psychological lesson. People naturally notice visible speed. Watching an agent create ten files in a minute feels productive. The slower costs are less obvious: reading those files, finding an incorrect assumption, rerunning tests, or repairing a change later. This difference between visible output and total completed work is why careful measurement matters.

Software development is therefore entering a more complicated stage of AI adoption. The important question is no longer whether machines can write code. They clearly can. The harder question is where their work reduces the total effort required to produce reliable software. As agents improve, that boundary will continue to move. For developers, the valuable skill may not be generating the most code with AI, but learning which tasks can safely be handed over, which ones require close supervision, and when writing the solution directly is still the fastest path.
