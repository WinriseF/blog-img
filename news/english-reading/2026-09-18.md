Why Software Is Moving Toward Memory-Safe Languages

A surprising number of serious computer security problems begin with something very ordinary: a program puts data in the wrong place in memory.

Every running program needs memory. It stores numbers, text, images, passwords, network packets, and many other things there while it works. Languages such as C and C++ give programmers very direct control over this memory. That control helped make them the foundation of operating systems, browsers, databases, and embedded devices. It also creates a difficult responsibility. The programmer must make sure that data is written only where it belongs and that memory is not used after it has been released.

When that responsibility is handled incorrectly, the result may be a memory safety bug. A program might write beyond the end of a buffer, use an object that no longer exists, or read memory that was never properly initialized. Sometimes the result is only a crash. In more serious cases, an attacker can use the mistake to read private information or make the computer run code chosen by the attacker.

These bugs are not rare accidents at the edge of software engineering. For years, major technology companies have reported that memory safety problems made up a large share of their serious vulnerabilities. In 2022, the U.S. National Security Agency noted that Google and Microsoft had each linked roughly 70 percent of their vulnerabilities to memory safety issues. That is why memory safety has moved from a specialist concern to a major topic in cybersecurity policy.

One of the clearest examples comes from Android. Google reported that memory safety issues represented 76 percent of Android vulnerabilities in 2019. By 2024, that share had fallen to 24 percent. Many changes contributed to the improvement, but Google has connected the decline closely with a shift toward memory-safe programming languages for new code.

A memory-safe language is designed to prevent many dangerous memory mistakes before they can become security problems. Some languages, such as Java and Python, manage much of a program's memory automatically. This works well for many applications, but low-level software often needs more predictable performance and closer access to hardware.

This is where Rust has attracted unusual attention. Rust was designed for systems programming, the area traditionally dominated by C and C++. It allows programmers to work close to the hardware while using rules that prevent many unsafe memory operations. Its most famous idea is ownership. In simple terms, the compiler keeps track of which part of a program owns a piece of data, how long that data remains valid, and when other parts are allowed to use it.

These rules can feel strict to new Rust programmers. Code that might compile in another language can be rejected because Rust cannot prove that the memory use is safe. That can make the learning process frustrating. But the same strictness changes when many bugs are discovered. Instead of waiting for a test, a security researcher, or an attacker to find the problem, the compiler can stop some classes of mistakes during development.

Android began supporting Rust for platform development several years ago. Google later reported that Android 13 was the first Android release in which most newly added code was written in a memory-safe language. The company did not attempt to rewrite the entire operating system. Instead, it focused on writing new components in safer languages and gradually replacing selected high-risk parts.

That detail is important because the software world contains an enormous amount of old C and C++ code. Rewriting it all would be expensive, slow, and risky. Old software may contain hidden bugs, but it also contains years of testing and fixes. A complete rewrite can remove old problems while introducing new ones.

For this reason, the current movement toward memory safety is mostly evolutionary rather than revolutionary. In 2025, the National Security Agency and the Cybersecurity and Infrastructure Security Agency published joint guidance encouraging organizations to adopt memory-safe languages where practical. The agencies also stressed that adoption does not require a complete rewrite. New modules can be written in a safer language and connected to existing software through carefully designed interfaces.

Large companies are following similar strategies. Microsoft announced in 2025 that it was rewriting SymCrypt, its open-source cryptographic library, in Rust while also using formal verification methods. Google has described using Rust in Android firmware and replacing selected components while keeping them compatible with existing C interfaces. The goal is not to declare one language the winner. It is to reduce the amount of security-critical code in which programmers must manually avoid every dangerous memory mistake.

Memory-safe languages are not a complete security solution. A program written in Rust, Java, or another safe language can still contain weak passwords, incorrect permissions, flawed business logic, insecure network design, or vulnerable dependencies. Rust itself also includes an “unsafe” mode for operations that the compiler cannot fully check. Low-level software sometimes needs this capability when interacting with hardware or older code.

Google provided a useful reminder in 2025 when its Android team described a memory safety problem found in Rust-based code before the affected component reached a public release. The issue showed that memory safety is not magic. It also showed the value of several defenses working together: the bug was found before release, and Android's hardened memory allocator made it non-exploitable in the tested environment.

For ordinary users, this shift may be almost invisible. Phones will not suddenly look different because part of an operating system was written in Rust. A browser will not open websites in a new way because a parser became memory-safe. The benefit is quieter. If developers can prevent an entire category of dangerous bugs before software is shipped, there are fewer opportunities for those bugs to become emergency security updates, data breaches, or attack tools.

For developers, the change is more visible. It asks them to move some responsibility from human discipline to language design and compiler checks. That can require new skills, new tools, and patience with stricter rules. It can also reduce the amount of time spent hunting a class of bugs that has troubled software for decades.

C and C++ are not disappearing. They remain deeply embedded in modern computing, and many projects will continue to depend on them. But the question facing software teams is changing. Instead of asking whether programmers can write safe low-level code with enough care, more organizations are asking why the language should allow certain dangerous mistakes in the first place.

That change in attitude may matter as much as the rise of any particular programming language. Software security has often depended on finding bugs after they are created. Memory-safe programming tries to move part of that work earlier, into the design of the language itself. The result is not perfect software, but a different starting point: fewer ways for a simple memory mistake to become a serious security failure.
