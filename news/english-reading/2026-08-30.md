Why AI Agents Need Sandboxes Before They Can Work Alone

For years, most artificial intelligence systems were mainly asked to produce information. A chatbot could answer a question, summarize a document, or suggest a piece of code. If it made a mistake, the result was usually a bad answer on a screen. The risk changed when AI systems began to act.

Modern AI agents can now open files, edit software projects, run commands, browse websites, call external tools, and sometimes send messages or change data. Coding agents are a clear example. They can inspect a repository, modify several files, run tests, and continue working until a task is finished. This makes them far more useful than a simple chatbot, but it also creates a basic security problem: an agent that can do useful work can also do harmful work if it is confused, manipulated, or given too much access.

This is why a familiar idea from computer security has become important again: the sandbox.

A sandbox is a controlled environment where a program can operate without receiving unlimited access to the rest of the computer. The idea is older than modern AI. Web browsers, mobile apps, and cloud services have used forms of isolation for years. What is new is the reason we now need it. An AI agent does not simply execute a fixed set of instructions written by a programmer. It interprets natural language, makes plans, chooses tools, and reacts to information that may come from outside sources.

That flexibility is exactly what gives an agent its power. It is also what makes its behavior harder to predict.

Consider a coding agent that is asked to fix a bug in a public software project. To do its job well, it may need to read source files, install dependencies, run a test suite, and perhaps search technical documentation online. During this process, the agent can encounter text written by people the user does not know. A malicious instruction could be hidden in a webpage, a document, an issue description, or even a file inside the repository.

This is known as indirect prompt injection. Instead of attacking the computer through a traditional software bug, an attacker places instructions in data that the AI is expected to read. The agent may then mistake those instructions for part of its task.

The danger becomes much greater when the model is connected to powerful tools. A misleading sentence is not very serious if the model can only produce text. The same sentence matters far more if the model can run shell commands, read private files, upload data, or call company systems.

Security researchers and technology companies have therefore started to focus less on the question, “Can we make the model obey perfectly?” and more on a different question: “What is the maximum damage the agent can cause if it makes the wrong decision?”

That shift is important because perfect obedience is unrealistic. Large language models are probabilistic systems. They can misunderstand instructions, follow misleading context, or behave differently when the same problem is presented in a new form. Human approval is useful, but it has limits too.

Anthropic, the company behind Claude, has described a problem called approval fatigue. Early versions of Claude Code often asked users for permission before writing files or running commands. In theory, this kept a human in control. In practice, people who see many approval boxes may begin clicking them automatically. Anthropic later reported that sandboxing reduced permission prompts in its internal use by 84 percent.

The lesson is simple: asking a person to approve every small action can create the appearance of safety without guaranteeing careful supervision.

A sandbox takes another approach. Instead of asking whether every action is safe, it limits what actions are possible in the first place.

For example, a coding agent might be allowed to read and write files only inside the current project directory. It may be blocked from reading a user's SSH keys, password files, browser data, or unrelated personal documents. Network access can also be restricted. The agent might be allowed to contact a small list of trusted services while being prevented from sending data to unknown servers.

OpenAI uses similar ideas with Codex. Its documentation describes sandboxed execution with network access disabled by default in important configurations, while higher-risk actions can require approval. The goal is not to assume that every command generated by an AI model is trustworthy. Instead, the system creates a boundary around what the agent can reach.

This principle is closely related to “least privilege,” one of the oldest ideas in cybersecurity. A program, employee, or service should receive only the permissions needed for a specific task. If an agent only needs to edit one repository, there is little reason to give it access to an entire home directory. If it only needs to download packages from known sources, unrestricted internet access may be unnecessary.

Recent security research shows why these boundaries matter. In 2026, Microsoft disclosed vulnerabilities in an AI agent framework where tool exposure could allow an attacker to turn prompt injection into real code execution. One problem involved file-transfer functions that gave the AI too much control over paths on the host computer. The issue was fixed by reducing what the model could call and by adding stronger path checks.

The episode illustrates an important point: a sandbox is not magic. A badly designed tool can accidentally create a bridge around it.

That means safe agent design requires several layers. The model should receive clear instructions. Untrusted content should be treated as data rather than authority. Tools should have narrow permissions. Sensitive credentials should stay outside the agent's working environment when possible. Network connections should be controlled. Important actions should be logged so that people can later understand what happened.

This layered approach is becoming more important as agents move beyond coding. An email agent may read messages and send replies. A business agent may update customer records. A cloud agent may create or delete computing resources. In each case, the central question is not only whether the AI is intelligent enough to complete the task. It is whether the surrounding system is designed to remain safe when the AI is wrong.

This may sound like a limitation on automation, but good boundaries can actually make agents more independent. If an agent operates inside a carefully designed environment, it can be allowed to work for longer periods without asking for constant human permission. Security and autonomy do not always have to move in opposite directions.

The most useful future agents may therefore look less like digital workers with unlimited access and more like skilled workers inside well-designed workplaces. They will have tools, freedom, and room to act, but also locked doors, clear responsibilities, and records of what they have done.

As AI agents become more capable, the quality of those boundaries may matter almost as much as the intelligence of the models themselves.
