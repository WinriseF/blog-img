When AI Writes More Code, Who Does the Reviewing?

Software developers once spent much of their time writing code line by line. That picture is changing quickly. Modern artificial intelligence tools can suggest functions, explain unfamiliar projects, fix tests, and even take an issue from a short description to a proposed pull request. The result is an unusual shift: producing code is becoming easier, while deciding whether that code should enter a real product is becoming more important.

This change helps explain why the debate about AI and developer productivity has become more complicated. A coding assistant can produce a working-looking solution in seconds, but software engineering is not simply the act of producing text that a computer can run. Code must also fit an existing system, survive unusual conditions, remain understandable months later, and avoid creating security or reliability problems. As generation becomes cheaper, verification can become the new bottleneck.

Research shows why simple claims about productivity should be treated carefully. In 2025, the research organization METR studied experienced open-source developers working on repositories they already knew well. Sixteen developers completed 246 real tasks. Before the experiment, they expected AI tools to make them about 24 percent faster. Even after the experiment, they believed AI had saved them time. The measured result was the opposite: with the early-2025 tools used in the study, the developers took 19 percent longer.

That finding did not mean AI coding tools were useless. The participants were highly experienced, their projects were mature, and the study captured a particular generation of tools. METR later reported that newer systems appeared more helpful, although problems in the later experiment made the exact size of the improvement uncertain. The broader lesson is more interesting than either result. The value of an AI assistant depends heavily on the developer, the task, the project, and the way the tool is used.

One reason is that generated code creates work of its own. A developer must read it, understand why it works, check whether it follows project rules, and test assumptions the model may have made. When a suggestion is almost correct, fixing it can take longer than expected. The developer may also need to inspect several files that the AI changed automatically. A tool can therefore reduce typing while increasing reviewing.

This is especially important as coding assistants become coding agents. An assistant usually waits for a developer and responds inside an editor. An agent can perform a longer sequence of actions: search a repository, edit several files, run commands, inspect test failures, revise its approach, and prepare a pull request. GitHub and other developer-tool companies are increasingly building products around this model. GitHub has described the emerging bottleneck not as generating software, but as reviewing, securing, governing, and deploying the growing amount of generated work.

The economics are easy to understand. Imagine that a developer can manually prepare four meaningful changes in a day, while AI allows the same developer to propose ten. If the team's ability to review changes remains fixed, the organization has not increased its useful output by two and a half times. It has increased the amount of work waiting for judgment. Faster generation can move the constraint from the keyboard to the review queue.

AI may also help with that second problem. A 2025 study of an AI-powered review system called DeputyDev examined more than 200 engineers in a controlled company experiment. The researchers reported a significant reduction in review time, including about a 23 percent reduction in average review duration per pull request. A later study from the same group, covering roughly 300 engineers over a year, reported shorter review cycles and higher code shipment among strong users of the system. These results suggest that AI can assist not only with creating code but also with processing the code that others create.

Yet automated review has the same basic weakness as automated generation: confidence is not proof. An AI reviewer may identify a suspicious change, but it can also miss a subtle error or complain about something harmless. Human reviewers have context that is difficult to capture in a prompt. They may know that a customer depends on an undocumented behavior, that a temporary design will be removed next month, or that a technically correct solution creates an operational burden for another team.

This makes software review less like proofreading and more like judgment. Tests can show whether known requirements are satisfied. Static analysis can catch certain classes of mistakes. AI can search for patterns across a large codebase. But someone still has to decide whether the change is the right change. That question includes technical concerns, product goals, cost, risk, and responsibility.

There is also a psychological problem. Generated code often arrives in a polished form. It has sensible variable names, comments, and a clear structure. This can make it feel more trustworthy than it deserves. A messy human draft signals that it needs attention. A clean AI draft may hide the fact that its author does not actually understand the system. Developers therefore need a new habit: judge generated code by evidence, not by appearance.

The same principle affects learning. Junior developers traditionally gain experience by struggling with implementation details and then receiving feedback from senior engineers. If AI performs much of the first stage, beginners may complete tasks faster while building a weaker mental model of the software. On the other hand, a well-used assistant can explain unfamiliar code, suggest tests, and expose a learner to approaches they might not discover alone. The difference depends on whether the developer treats the tool as a substitute for understanding or as a way to reach understanding faster.

For engineering teams, this means that counting generated lines of code is becoming even less useful as a measure of productivity. More code can mean more features, but it can also mean duplication, maintenance work, and a larger surface for bugs. Better measures focus on outcomes: how quickly valuable changes reach users, how often deployments fail, how long reviews take, and whether developers can safely maintain what has been built.

AI is changing software development partly because it makes creation abundant. That abundance does not remove engineering work; it changes where the difficult work happens. When code was expensive to produce, writing it was a central constraint. As machines become capable of producing far more of it, attention, verification, and judgment become relatively scarce. The developer of the AI era may type less, but the responsibility to understand what enters the system does not disappear. In many cases, it becomes the most important part of the job.
